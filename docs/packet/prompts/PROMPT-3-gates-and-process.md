# PASS 3: gates and process design (new chat)

You are a release-engineering and safety reviewer for a data website where a wrong number could mislead someone near a flooding river. The site is built by an AI assistant for a non-coder owner and is meant to grow from 25 pages to about 9,500. Read `README-FIRST.md`, `00-CONTEXT.md`, `MANIFEST.md`, then `code/CLAUDE.md` (section "Gates that stop a deploy"), `code/refresh.py`, `code/check.py`, `code/tests.py`, `code/truth_tests.py`, `code/ui_gates.mjs`, `code/tools/gate_plan.py`, `code/tools/truth_live.py`, `code/tools/watchdog.py`, `code/.github/workflows/refresh.yml` and `watchdog.yml`, `code/lib/reviewgate.py`, `code/tools/record_review.py`, and the evidence files `evidence/ci-runs.txt`, `evidence/ci-run-gates.log`, `evidence/gate-output.txt`. Skip everything else.

1. Gate inventory. A table: gate | where it runs | what it actually checks (from the code, not the docs) | can it refuse a release (yes / no / only after deploy) | the class of defect it cannot see. Mark any gate described in the docs but not wired into the release chain (`refresh.py` is the chain; `tests.py` and `check.py --selftest` are run by hand).
2. Failure analysis. For each failure below say which existing gate catches it (if any) and what the reader would see: a source returns another gauge's data; a source is down for 24 hours; the alerts API errors and the page says there are no alerts; a unit change (cfs/kcfs, ft/m); a sentinel value; a gauge disappears or is renamed; USGS changes the response shape; the GitHub scheduled workflow stops (note the observed cadence in `ci-runs.txt` and that GitHub disables schedules on inactive repositories); a gate fails for an unrelated reason (font, flaky browser) and freezes data; two deployers race (GitHub and the owner's PC); a cohort of new pages is judged thin by search engines; a wrong number during a real flood.
3. Fail-open versus fail-closed. For a flood-information site, which gates should block, which should degrade the page (label it stale), and which should alert only? One table. Judge the current rule (a template change needs a signed review; a data refresh with an unchanged template skips the browser layout gates).
4. Proposed gates. The ten most valuable missing gates, in priority order. For each: the defect class; the exact check (regex, DOM rule, numeric tolerance, API comparison); where it runs; one fixture that must FAIL it and one that must PASS; what it must never flag; effort in hours; false-positive risk. Include at least: a blocking truth check against a second source; physical-range and stuck-sensor checks over every gauge type (tidal, regulated, ice-affected, estuary, canal, no statistics), not only the 25 pilot gauges; "source failed" must never render as "nothing to report"; gauge-type eligibility at the queue; a post-cohort measurement go/no-go from Search Console; an external monitor that does not depend on GitHub; reviewer independence for the AI review step.
5. Process design. The project runs repeated "fresh-brain" AI reviews (about 15 rounds in `late/FRESH-REVIEW-10-*`). Judge the process: what did it find, how many findings became gates, is it converging, what does it cost, what should replace it at 1,000 pages (sampling, canary pages, real users, outside reviewers)? Give the smallest change set that makes the process self-correcting and a stop rule.
6. What you could not determine from the packet and what you would need (logs, run history, secrets handling).

Rules: label claims [SEEN IN PACKET] / [MY KNOWLEDGE, UNVERIFIED] / [GUESS]. If a gate is theatre, say so and why. Do not list gates that are not in the packet as if they exist. At most 2,500 words. Start with a one-paragraph verdict: would these gates stop the next serious mistake? Yes, no or partly, with the single biggest hole.
