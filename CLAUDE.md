# River Water Levels (riverwaterlevels.com)

One static page per USGS river gauge. Government data only (USGS, NOAA/NWS, USDA, EPA). Ad-supported later. The owner is a non-coder and never runs commands: do the work, short plain replies, no "Next:" line, decide defaults yourself. This folder is its own project; the car-repair site's rules do not apply here.

## Line 0 (HARD, owner 2026-10-23): this is the absolute most useful river page on the internet
Every public dataset that answers a real question about this river for any water user goes on the page, with its exact source and the time. We maximise information gain and close every data gap: if a reliable public feed carries a value a reader would want, we show it; a gap stays only because no trustworthy public feed exists (wrong, misleading reporting-habit, padding, or no mechanism are the only reasons to withhold). No other page in the world should carry more useful, sourced river data than ours. When in doubt whether a dataset belongs, the answer is show it with its caveat, not hide it.

## Line 1 (HARD, owner 2026-10-23): user first, clean UI, never Google first
The page is built for the person at the river, not for a search engine. Every block earns its place by helping that reader decide, in seconds, on a phone; the layout stays clean and presentable (one page colour, white cards, one label and numeral style, unit beside the number, one line under each number, data age said once). No SEO gaming, no keyword stuffing, no doorway pages, no padding for ranking. If a choice helps Google but not the reader, we do not make it. Usefulness and clarity beat page count and search tricks every time. We reach #1 only by being the single most helpful result a person can land on for this river; when a page is not good enough we make it more helpful, never hide it — noindex is never the fix for a thin page (a thin page fails the build until it is enriched; the wave rollout and embed widgets are the only noindex, and every reader page is indexed once it is rich and crawled).

## How we decide (HARD, owner 2026-10-27: "smart like Elon Musk"): the five steps, in this order, on every change
1. Question the requirement: who asked, what reader problem it solves, what proves it (an owner rule is questioned too, then followed or pushed back on with evidence). 2. Delete: remove a part, step, duplicate or check before adding one; if nothing ever has to be added back, too little was deleted. Delete applies to code, process, repeated text and machinery, NEVER to river conditions: Line 0 wins, every public dataset a reader at this river could use stays on the page (a block is cut only for the four valid reasons: wrong, misleading, padding, no mechanism), and a hater finding is fixed by making the data clearer, never by hiding it. 3. Simplify what is left: one path per job (one live-readings path, one hourly run, one gates file). 4. Accelerate: shorten the loop from change to proof (one batch, gates once, read live). 5. Automate last: a rule or script only after a person (the hater) has found the problem by looking. Never optimise or automate something that should not exist. Measure, never assume (40 visitor requests = 0 USGS calls was measured, not argued).

## Line 2 (HARD, owner 2026-10-27): no page goes live until the worst hater in the world has looked at it
Text rules cannot see a page; a reviewer must. Enforced in `check.py` (`review_gaps`): every live gauge needs a signed PASS in `state/reviews/<site>.json`, and any change to page code (`lib/`, `templates/`, `build.py`, `collect.py`, `worker/index.js`: `template_hash()`) needs a fresh PASS of `_template` before it deploys, reviewed on the pages `python -I tools/hater_sample.py` picks (the fewest pages that together show every block and page situation). Every new gauge gets its own review before it goes live: FIRST mode (owner 2026-10-28, about 10x cheaper) = the phone and desktop first screen plus the whole page text against the fixed FAIL LIST (F1-F8 in `.cache/review/_brief.md`); FULL mode (every screenshot) = the `_template` sample and any gauge bringing a data shape no reviewed page had (Boise: impacts published as flow). Every signature is appended to `state/reviews/_log.jsonl`; each new FAIL type becomes a `check.py` rule with a fixture in the same round. Hourly data refreshes do not change code and keep running.
How: `node tools/hater_shots.mjs [sites]` saves what a visitor sees (`.cache/review/<site>/`: phone slices, desktop first screen, text). A reviewer who did NOT build the change reads every image and the text with the brief below, then `python -I tools/review_sign.py <site|_template> PASS|FAIL "defects, worst first"`. One defect a reader would notice = FAIL. Fix at the cause, re-shoot, re-review. Never sign what you did not look at.
The gates learn from the hater: every defect a machine could have caught (cut-off text, a contradiction between two numbers, a label with no unit, "tidal" without a tide station) becomes a `check.py` rule with a planted-bug fixture in the same batch as its fix, so the next hater only finds what no rule can see. A defect class found twice by a hater with no rule written is a process failure.
Review economics (5-step, owner 2026-10-27): a gauge's PASS stands; a code change is re-checked by the `_template` sample on the new code plus every `check.py` rule on all pages, never by re-reviewing every passed page. Human eyes per page only for a new gauge, a FAIL, or a data shape the sample does not cover. Fix in shared code so one fix reaches every page. A derived line (not river data) that needs a third fix is deleted, not patched (2026-10-27: "Last 20% rise", "measured lag"). Reviewers take 3 pages each, 2 at a time (image limit); a slice not seen is a FAIL. Past ~1,000 gauges per-page review stops: new pages ship on the rules plus a data-shape sample.
Truth, not agreement (owner 2026-10-27, flood-site lesson: its gates checked numbers against each other and garbage shipped): the API numbers are never where we fail; our sentences about them are (wrong zero point, rain scenarios shown as impacts, "Steady" in a 7% drop). Every derived number is checked against the source API fetched now (`tools/truth_live.py`: readings, flood stages, every "NWS ... stage X ft (D ft above ...)" and "Next NWS impact" line, and the zero-point match), never against our own calculation. A sentence no source can check is deleted. A hater FAIL takes the gauge off the site at once (`review_sign.py` sets it back to queue); `release.py` returns it only after a PASS. One plan file per site: this CLAUDE.md; competing plan and prompt docs are archived, not kept beside it.
Hater brief (give it verbatim to the reviewer): "You hate this site and want to prove it is wrong, confusing or lazy. You are a person at this river with 30 seconds on a phone. For every screen: any number that is wrong, contradicts another number on the page, or has no unit, time or source; any label that does not say what the number is; any text cut off, overlapping or unreadable; any jargon; anything said twice; any block that does not help someone deciding about this river today; any 'not measured' or '-' where a public feed has the value; anything a competitor (snoflo.org, water.noaa.gov, USGS) shows better. You also know exactly what it takes to rank #1 on Google for '<river> <place> water level' and '<river> flow': judge as a Google quality rater and as the searcher who clicked. Does the first screen answer the search at once (level, flow, is it normal, is it safe-relevant, when measured)? Does the title and H1 match what people type? Is it plainly more useful than the current #1 result, with something no other page has? Is trust visible (who measured it, when, exact source links)? Anything that reads as mass-produced, thin, padded, repeated across pages, slow or cluttered on a phone, or that would make a searcher go back to Google, is a FAIL. Quote the exact text and image file. Worst first. PASS only if you found nothing a reader or a quality rater would mark down."

## The procedure (HARD, owner 2026-10-21: "it's just APIs on pages, it shouldn't keep fucking up")
Every change, no exceptions:
1. Say in one line what will change. Nothing that runs gates or a deploy starts until the owner says go.
2. Change code through a script file (Write, then run), never a shell heredoc. One batch of edits, then one check run.
3. Build. Look at two screenshots of one page (phone and desktop) before anything else runs.
4. `python -I gates.py` once (two gates). A failure is fixed at its cause, never by loosening or deleting the check. A third failure on one check means stop and report the cause.
5. Commit with explicit paths. A push is a deploy. Read the live page. "Done" means read live this turn.
6. One line in docs/OPEN-ITEMS.md's done log with the proof.
Adding gauges: `python -I tools/release.py N` prints the full gauge names; read them (wrong place or wrong gauge: fix the list first); it collects and builds the pages. Then release -> push -> `tools/open_wave.py N --apply` -> push -> `tools/index_live.py`.
A rule without a check is a note. A check not in `gates.py` does not exist.
Gates (rebuilt 2026-10-25, first principles): they BLOCK only what would show a reader something wrong (it builds; it is true). Whatever can heal (site not rebuilt, missing gauges, a dead feed, stale edge readings) never blocks a deploy: `tools/watchdog.py` heals it hourly and reports it, and never emails (owner: no alarms). Every new check ships with a planted-bug fixture that fails with its own message (`check.py --selftest`). Session start: `python -I tools/watchdog.py` (live health: problems first).
Live layer (simplified 2026-10-26, owner: "simplify"): ONE path for live readings. A */3 cron in `worker/index.js` asks USGS only what CHANGED since its cursor (last_modified) and keeps ONE stored copy in KV; phones never call USGS, they re-read `/live/<site>.json` when the tab comes back and every 5 min while visible. The same cron starts the hourly GitHub build when the deployed build is over 40 min old (needs the Worker secret GH_DISPATCH_TOKEN, a key that can only start workflows on this repo). Every gauge page reads that copy (no USGS call on any page view: crawlers cost nothing), swaps the reading in and stamps every `dv` element with the build reading's time; flagged readings are never swapped. Cost: ~20 USGS calls/h at any traffic; ~5 KB stored at 53 gauges. Never fetch-on-open per gauge: it spends the key per city per crawler and dies on flood days. Google rule (owner: "no Google penalty"): Googlebot and a phone always get the same page, and everything a reader or Google needs is in the HTML; the browser may only refresh numbers, never be the only place content exists (watchdog checks parity). Cloudflare free plan limits are per ACCOUNT, shared with asmrregistry: 5 crons, 100,000 worker requests/day, 10 ms CPU, 20,000 files.

## Reader (Line 0, owner 2026-10-20: "every data block for every water activity, in priority for the user")
A person at or near this river today, on a phone, about to fish, paddle, swim, tube, wade, boat, row, dive, pan, hunt, camp, guide, or who lives, drives or rescues beside it. Flood watchers are one reader among twenty, not the first. Every page answers, in this order: is it dangerous now, what is the water like, is it normal, what is coming, how today compares. Correct is necessary, never enough: the page must be understood in seconds and look made by a person (design review 2026-10-21 against Lakebrief: one page colour, white 12 px cards, one label style, one numeral face, unit beside the number, one line under each number, the data age said once).

## Every gauge page, in this order, nothing collapsed on the Now tab
1. Alert banner (NWS, live) when one is active.
2. H1, gauge id, one age chip ("56 min old"), one observed time. Age is stated once.
3. Tiles: latest flow, gage height (sparklines), is-this-normal (percentile bar, words), 6 h change, NWS forecast high or "Not issued", water temperature (or the nearest same-river sensor, or "not measured"), rain 24 h, air (temperature, wind, gusts), sunset (sunrise, last light, moon). Every tile: label, number, unit, one line, time.
4. What the water is like now: sensors (temperature, turbidity, dissolved oxygen, pH, conductance, salinity, velocity, nitrate; USGS qualifiers such as Ice printed), tides on tidal reaches (detected: flow cycles within the day, `oscillating()`), hourly weather with thunder and humidity, rain here and at nearby stations.
5. Level, flow and flood risk: 7-day chart with a range switch (`merge_charts` folds 30 days, 12 months and earlier years into it), gage height with the flood-stage ladder, NWS impact statements, rate of change.
6. Forecast on every river: NWS river forecast or "Not issued", National Water Model guidance, rain outlooks.
7. How today compares: month, year, same dates in earlier years, record, water temperature by month, snowpack.
8. Closed folds: flood record, daily values and rating, watershed and land. Right column (the "Area" phone tab): upstream and downstream, nearby, NWS point, map, official links, about. Phone tabs Now / Forecast / History / Data / Area come from `GROUP_OF` and the `SEC:` headings in `lib/render.py`.

## Never shown
"Safe", "runnable", "fishable" or any verdict; composed sentences other than labels and verbatim attributed source text; a number without unit, time and Source line; a block whose source in `data/sources.json` is not `quoted` or `owner-permission` (`off` sources are built, never shown); a missing source as silence (the gaps line says "Not measured at this gauge: ..."); data older than its limit as current (flow 24 h "not reporting", 30 d not rebuilt; river forecast amber 24 h hidden 72 h; weather obs 3 h / 12 h; hourly forecast amber 12 h hidden 72 h; alerts 3 h; rain 6 h; water temperature tile only under 24 h; the Methodology page states the limits). NWS "Test Message" and "Administrative Message" alerts are ignored (`IGNORED_ALERTS`).

## Every block has four states (tests enforce them)
valid: value, unit, time, Source line. valid-empty: the source said "nothing", printed as a sentence, never silence. unavailable: "Unknown" or "unavailable", never "none"; a block that cannot build is hidden by the guard and logged, and the gaps line names it. stale: the real age, marked old. `SAFETY_BLOCKS` (alerts, river forecast, impacts, stage and flow charts, offline, flood stages, no-forecast, NWS point) fail the gauge and keep its previous page; every other block hides alone. A source record is a dict with the field types in `data/cache_shape.json`; anything else counts as empty.

## How a change ships
- `collect.py` is the only network code. One hourly run, each source on its own timer: USGS readings, NWS, NWPS, rain and WPC every run; tides, cameras, air quality and the other extras every 6 h; history, the full 8-day USGS series and the `DAILY` set once a day; a new gauge's first run is a full collect. `build.py` reads `cache/` only (`--preview` shows uncleared blocks). Keys live in the calcscrape `.env`, read by `lib/common.py` only; never in pages, zips or docs.
- Batch edits, then `python -I gates.py` ONCE per batch. The two gates live in `gates.py` and nowhere else; `refresh.py` runs the same list. A rule that is not in `gates.py` is a note. `check.py` page weight limit 90 KB gzipped fails the build; change the number in the file with a reason, never silently.
- Deploys run only through `.github/workflows/refresh.yml` (push to main, schedule, or `gh workflow run refresh.yml`). Then `python -I tools/index_live.py` reports 0 mismatches and read one live page body. "Live" means read this turn.
- Windows: PowerShell has no `&&`; Git Bash needs `MSYS_NO_PATHCONV=1` for `/paths/`; `python -I` drops the script folder from `sys.path` (scripts insert ROOT). Never write code through a shell heredoc; write a script file.
- Commit with explicit paths. Trailer per the current attribution reminder.

## Adding gauges (the site grows here)
- `python -I tools/release.py N` takes the next N gauges from the priority list (`docs/research/priority/picks.csv`, the owner's order; the formula in `tools/rescore.py` is a tiebreaker), marks them live in `data/waves.csv`, collects them in full and builds them. A new page goes into Google only through `tools/open_wave.py N --apply`. One river, one gauge first: the gauge nearest the put-in or the fishing town; more gauges on the same river come later.
- The scheduled refresh covers EVERY gauge with a cache file (`collect.py` with no site arguments; never a hard-coded list). A page that is not refreshed every 30 minutes is a wrong page.
- Scale ceilings (audit 2026-10-21 at 25 gauges, `docs/research/SCALE-AUDIT-2026-10-21.md`; nothing below is built yet). First break is the fast run at about 70 gauges: collect.py is sequential with a 1.5 s gap and 13 to 20 calls per gauge (24 s per gauge), so the 30 min cron queues behind itself. Before 70: fast lane = the bulk USGS call only (40 gauges per call), alerts once per state, the static NWS lookups cached; weather, NWPS and rain move to the 6 h lane. Before 150: the 6 h lane becomes a GitHub matrix job sharded by state with a TTL per source (USGS OGC key allows about 1,000 calls/h). Before 5,000: build.py renders per gauge instead of loading every cache (4.7x JSON in memory). Before 16,000: Cloudflare Workers Paid ($5/mo) for the 100,000-file asset cap and raise FILE_BUDGET in build.py. Also: truth_live and index_live sample changed pages past 400; the TX state page passes the 480-link budget near 14,000.
- Pace: 25 a wave; the next wave opens when the last one has been crawled and no number incident happened. Order is re-cut from Search Console queries once the owner verifies the property.
